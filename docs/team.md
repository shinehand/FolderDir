# FolderDir 프로젝트 팀 구성 (Project Team Structure)

> 작성일: 2026-03-31  
> 목적: 기획팀과 개발팀의 역할·책임·협업 프로세스를 명문화하여 일관성 있는 개발 진행

---

## 1. 팀 구성 (Team Composition)

### 1.1 기획팀 (Planning Team)

| 역할 | 인원 | 주요 책임 |
|------|------|-----------|
| PM (Product Manager) | 1명 | 전체 로드맵 관리, 우선순위 결정, 리더 컨펌 조율 |
| UX 디자이너 | 1명 | 사용자 흐름 설계, 화면 설계, UX 인터랙션 명세 |
| BA (Business Analyst) | 1명 | Q-Dir 비교 분석, 기능 요구사항 명세, 갭(Gap) 분석 |
| QA 담당자 | 1명 | 구현 검수, 버그 분류, 수락 기준 작성 |

#### 기획팀 책임 (Planning Team Responsibilities)
1. **현황 파악** — 현재 구현된 코드(`src/`)와 기획서(`docs/planning.md`)를 주기적으로 전수 검토
2. **문제 발굴** — UX 관점(사용자 체감), 기능 누락, 버그, Q-Dir 대비 차이를 목록화
3. **상세 기획 작성** — 각 기능의 사용자 시나리오, UI 와이어프레임, 인터랙션 패턴, 수락 기준을 명세
4. **개발 요청** — 기획 문서를 `docs/planning.md` 신규 섹션(`§0.X`)으로 작성하여 개발팀에 전달
5. **검수** — 구현된 기능이 기획 명세와 일치하는지 테스트 후 완료 표시

### 1.2 개발팀 (Development Team)

| 역할 | 인원 | 담당 영역 |
|------|------|-----------|
| 개발 리더 | 1명 | 아키텍처 결정, 업무 분배, 코드 리뷰, 기획-개발 인터페이스 |
| 개발자 A | 1명 | 파일 작업 백엔드 (FileOps·CRC·ZIP·폴더 비교·휴지통) |
| 개발자 B | 1명 | UI 컴포넌트 (FolderPane·탭·브레드크럼·색상·사이드바) |
| 개발자 C | 1명 | 기반 시스템 (레이아웃 매니저·패널 동기화·i18n·PDF·포터블) |

#### 개발팀 책임 (Development Team Responsibilities)
1. **기획 검토** — 기획팀이 작성한 섹션을 숙독하고, 기술적 타당성·난이도·의존성 평가
2. **업무 분배** — 리더가 충돌 없이 각 개발자에게 서브태스크를 배정 (§0.4 스프린트 계획 기준)
3. **아키텍처 원칙 준수** — 기존 클래스 구조 유지, Qt 표준 API 우선, 스레드 안전성 확보
4. **구현** — 속도와 정확성을 우선으로, 회의를 거쳐 최적 구현 방식 결정 후 착수
5. **문서화** — 구현 완료 후 `docs/planning.md` 해당 항목을 `✅ 완료`로 갱신

## 2. 협업 프로세스 (Collaboration Process)

```
기획팀                          개발팀
  │                               │
  ├─ 1. 현황 분석 ───────────────→│  기획 검토 요청
  │   (코드·기획서 전수 검토)      │
  │                               │
  ├─ 2. 상세 기획 작성 ──────────→│  기획서 수신
  │   (시나리오·와이어프레임)      │
  │                               │
  │                         리더 컨펌
  │                               │
  │                         ├─ 업무 분배
  │                         ├─ 개발자 A: 파일 작업
  │                         ├─ 개발자 B: UI
  │                         └─ 개발자 C: 시스템
  │                               │
  │                         ├─ 구현
  │                         └─ 코드 리뷰
  │                               │
  ├─ 3. 검수 ←───────────────────┤  구현 완료 알림
  │   (수락 기준 확인)             │
  │                               │
  └─ 4. 완료 확인 ───────────────→│  planning.md ✅ 갱신
```

## 3. 스프린트 진행 규칙 (Sprint Rules)

1. **2주 단위** 스프린트 진행 (§0.4 계획 기준)
2. 각 스프린트 시작 전 **리더 컨펌** 필수 (§0.5 체크리스트 사용)
3. 충돌 방지를 위해 같은 파일을 동시에 수정하지 않도록 리더가 사전 조율
4. 스프린트 종료 후 기획팀 **검수 → 완료 표시** → 다음 스프린트 착수
5. 긴급 버그(🔴)는 현재 스프린트 중단 없이 병행 처리 (Sprint 5.5 선례 참조)

## 5. 연락 및 의사결정 채널 (Communication & Decision Channels)

- **기획 → 개발**: `docs/planning.md` 신규 섹션 추가 + GitHub Issue 생성
- **개발 → 기획**: GitHub PR Description 으로 구현 내용 공유
- **긴급 결정**: GitHub Issue 에 `🔴 urgent` 레이블 부착 후 리더 멘션
- **리더 컨펌**: `docs/planning.md` 해당 체크리스트 항목 체크로 승인
